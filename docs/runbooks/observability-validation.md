# Runbook – Observability Validation

**Applies To:** CloudOps Event Platform  
**Release:** v0.4.0

---

# Purpose

This runbook verifies that the observability capabilities of the CloudOps Event Platform are functioning correctly.

It confirms that logs, metrics, dashboards, alarms, health endpoints, and notification mechanisms are operating as expected.

Execute this runbook after:

- Infrastructure deployment
- Application deployment
- Monitoring configuration changes
- CloudWatch dashboard updates
- Alarm configuration changes

---

# Scope

This runbook validates:

- Structured logging
- Correlation identifier propagation
- CloudWatch custom metrics
- CloudWatch dashboard
- CloudWatch alarms
- Amazon SNS notifications
- Health endpoint

---

# Prerequisites

Before beginning, verify:

- API is running.
- Worker is running.
- AWS infrastructure has been deployed.
- CloudWatch Dashboard exists.
- CloudWatch Alarms exist.
- Amazon SNS Topic exists.
- AWS credentials are valid.

---

# Procedure

## Step 1 – Verify Health Endpoint

Call the API health endpoint.

Example:

```bash
curl http://localhost:5000/health
```

Expected response:

```
HTTP 200 OK
Healthy
```

---

## Step 2 – Submit a Test Event

Submit a valid event.

Example:

```bash
curl -X POST http://localhost:5000/events \
-H "Content-Type: application/json" \
-d '{
      "eventType":"OrderCreated",
      "source":"Runbook",
      "payload":{
          "orderId":"ORD-1001",
          "customerId":"CUST-2001",
          "amount":149.99
      }
}'
```

Record:

- EventId
- CorrelationId (if returned)
- Submission time

---

## Step 3 – Verify API Logs

Confirm the API logs include:

- Event submission
- EventId
- CorrelationId
- EventType
- Source

No unexpected exceptions should appear.

---

## Step 4 – Verify Worker Logs

Confirm the Worker logs show:

- Message received
- Event processing started
- Persistence completed
- Message deleted

Verify the CorrelationId matches the API logs.

---

## Step 5 – Verify CloudWatch Metrics

Open CloudWatch Metrics.

Confirm the following custom metrics exist and update appropriately:

| Metric | Expected Result |
|---------|-----------------|
| EventsAccepted | Increments after API submission |
| EventsProcessed | Increments after successful Worker processing |
| DuplicateEvents | Increments only when duplicate EventIds are processed |
| EventsFailed | Remains unchanged during successful processing |

---

## Step 6 – Verify Dashboard

Open the CloudWatch Dashboard.

Confirm that dashboard widgets display current values for:

- Accepted events
- Processed events
- Duplicate events
- Failed events
- Alarm status

No widgets should report errors or missing data.

---

## Step 7 – Verify Duplicate Detection

Submit the same EventId again using a controlled duplicate test.

Confirm:

- DynamoDB does not create a second record.
- Worker logs a duplicate detection event.
- DuplicateEvents metric increments.
- EventsProcessed does not increment for the duplicate.

---

## Step 8 – Verify Alarm Configuration

Open CloudWatch Alarms.

Confirm:

- DuplicateEvents alarm exists.
- EventsFailed alarm exists.
- Both alarms are in the **OK** state under normal operation.

---

## Step 9 – Verify SNS Notifications

Generate a controlled alarm condition (if safe to do so in the current environment).

Confirm:

- CloudWatch changes the alarm state.
- Amazon SNS publishes a notification.
- The configured subscriber receives the notification.

After verification, return the environment to a healthy state.

---

# Verification Checklist

The validation is successful when:

- Health endpoint returns **HTTP 200 OK**.
- Structured logs are generated by both API and Worker.
- CorrelationId is preserved across services.
- Custom CloudWatch metrics update correctly.
- Dashboard displays current operational data.
- Alarms exist and report healthy status.
- SNS notifications are delivered when alarms are triggered.
- Duplicate processing is detected without creating duplicate records.

---

# Expected Results

A successful validation demonstrates that the platform provides end-to-end operational visibility, including:

- Service health
- Event correlation
- Operational metrics
- Dashboard visualization
- Alarming
- Notification
- Idempotent processing visibility

# Troubleshooting

## Health Endpoint Unavailable

Possible causes:

- API not running.
- Routing configuration issue.
- Application startup failure.

Verify:

- API logs.
- Application configuration.
- Endpoint registration.

---

## Metrics Missing

Possible causes:

- CloudWatch metric publisher not executing.
- Incorrect AWS Region.
- Missing IAM permissions.

Verify:

- Metric publisher logs.
- CloudWatch namespace.
- IAM policy.

---

## Dashboard Shows No Data

Possible causes:

- Incorrect metric namespace.
- Metrics not yet published.
- Dashboard widget configuration.

Verify:

- CloudWatch Metrics.
- Dashboard JSON.
- Metric names.

---

## Alarm Never Triggers

Possible causes:

- Incorrect threshold.
- Wrong metric selected.
- Insufficient evaluation periods.

Verify:

- Alarm configuration.
- Metric dimensions.
- Evaluation period settings.

---

## SNS Notification Not Received

Possible causes:

- Subscription not confirmed.
- Incorrect topic configuration.
- Alarm action not configured.

Verify:

- SNS subscription status.
- CloudWatch alarm actions.
- Topic permissions.
